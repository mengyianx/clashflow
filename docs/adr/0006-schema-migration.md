# v2 破坏性迁移：schema 版本 + 自动备份 + 禁止降级

状态：已接受（2026-11-06）。

现有数据库只有一种升级机制：`MetadataStore.__init__` 里逐列 `ALTER TABLE ... ADD COLUMN`，约定「只往元组里追加列，永不改 CREATE TABLE 体」。它能撑住 V1 的几次加列，但撑不住 V2：配置要拆成源与运行、订阅与配置的隐式同名关联要显式化、Overlay 与统计表要新增。没有版本号就无法判断「这个库是谁写的」，也无法在库比镜像新时阻止启动。

## 决定

- 引入 `PRAGMA user_version` 作为 schema 版本，配合有序迁移链（每个版本一个不可变函数）；每次启动先读版本、再决定是否迁移。
- **迁移前自动备份**：`/data/clashflow.db` 与 `/data/configs/` 整体复制到 `/data/backup/v<from>-<UTC 时间戳>/`，备份失败即中止迁移。
- **版本门禁**：库版本高于镜像 → 拒绝启动并提示「该数据卷已被更新版本的 ClashFlow 使用」；低于 → 自动迁移到当前版本。
- **迁移内容**：把订阅与源配置的关系显式化（列或关联表，实现时定，但不再依赖「同名即归属」）；新增 Overlay、统计与采样相关对象；为首个 Active 源配置渲染一次运行配置（其余配置按需渲染），内核 `-f` 改指 `/data/runtime-configs/`。
- **不让旧代码读新库**：迁移后的库不再保证可被 v1 读取；回退路径只有「停容器、还原备份、拉回 v1 镜像」一条，写进迁移说明。

## 后果

- 镜像降级从「拉旧 tag 就行」变成「先还原备份」；版本门禁把静默的数据损坏变成明确的中文报错。
- 每次升级都会在 `/data/backup/` 留下整份配置与库的副本，卷会变大；不自动清理，交给用户。
- 迁移函数一旦发布就不可改（历史库可能停在任意版本），新增改动只能追加新版本。

## 备选方案（未采用）

- **沿续「只加列」约定**：做不到拆表与关系显式化；且无法用二进制层面拒绝降级。
- **手动迁移命令**（`clashflow migrate`）：时机可控，但家用场景下多一步就多一次「容器起不来」的求助；自动迁移 + 自动备份已经能覆盖回退需求。
- **不迁移，要求用户重建配置**：把成本全部推给用户，与「允许一次性破坏性迁移」的决定相反。
