# ADR-0003：内核与运行面板的运行时更新

状态：已接受（2026-11-05）

## 背景

此前三个上游产物都钉死在镜像里：mihomo `v1.19.32`、metacubexd `v1.273.1`、zashboard `v3.30.0`。`docs/scope.md` 明确写着"容器内升级内核"不做，升级 = 拉新镜像重建容器。

这带来两个现实问题：

1. 内核小版本修复（协议兼容、规则解析）通常只想换个二进制，不值得为它重建并发布一次镜像。
2. 运行面板（metacubexd / zashboard）是纯静态包，更新频率远高于面板本体；让用户等镜像发版没有意义。

OpenClash 的做法是可参照的先例：面板里"检查更新 → 一键更新"，下载后校验、原子替换、内核更新后重启。

## 决定

三个产物都支持**手动**运行时更新，镜像仍是默认基线：

- **触发**：面板"系统"页手动"检查更新"，用户点"更新"才下载安装。不做自动安装。
- **来源**：只查 GitHub Releases 的 `latest`（`MetaCubeX/mihomo`、`MetaCubeX/metacubexd`、`Zephyruso/zashboard`）；`CLASHFLOW_GITHUB_PROXY` 可加统一前缀，供 GitHub 不稳定时走代理。不接受界面填任意 URL。
- **落盘**：装在数据卷 `/data/runtime/` 下，容器重建后仍然是用户装的版本；每个组件保留上一版用于一键回滚。
- **切换**：`current` 是指向版本目录的符号链接，用 `os.replace` 原子替换；两套运行面板的静态挂载按请求解析 root，所以换包立即生效、不重启。
- **内核更新**：停内核 → 换指针 → 用当前配置重新启动 → 探活。新二进制没起来就回滚指针、重启旧内核并报错；原来处于停止状态时只换文件，不替用户启动。
- **校验**：GitHub 提供 `sha256` digest 时逐字节校验；无论有没有 digest，都先解包压缩流、跑一次 `mihomo -v`，面板包还要通过入口检查（`index.html` 存在、其引用的本地 js/css 存在、至少一个脚本），与 OpenClash 的目录校验同构。
- **并发**：同一组件同时只允许一个更新操作，第二个请求返回 409。

## 后果

- 镜像不再保证"跑的就是镜像里的版本"；系统页会显示每个组件的 `来源：镜像 / 已更新`。
- 引入新的供应链面：从 GitHub 下载二进制并在本机执行。缓解手段是 digest 校验、`-v` 冒烟、面板包入口校验、保留上一版可回滚；没有引入签名体系。
- 数据卷会多出 `/data/runtime/`（每组件当前版 + 上一版）；不做自动清理更早的版本。
- 只跟 `latest`：无法钉具体版本，也无法从被撤回的版本回退到更旧的非上一版。
- 上游改资产命名（例如 mihomo 的 `mihomo-linux-<arch>-<tag>.gz`）会让更新失效，报错会明确指出缺失的资产名。

## 备选方案（未采用）

- **保持仅镜像内更新**：可复现性最好，但内核/面板小版本修复必须发镜像，代价与收益不匹配。
- **自动安装最新版**：省事，但把未经验证的版本直接推上家用网关；与 ADR-0001 的"内容归属用户"气质也不符。
- **只更新到容器临时目录**：实现最省，但容器重建即丢失，用户会以为更新没生效。
- **允许任意下载 URL**：OpenClash 支持，但多一个信任面；用环境变量前缀代理已覆盖主要场景。
